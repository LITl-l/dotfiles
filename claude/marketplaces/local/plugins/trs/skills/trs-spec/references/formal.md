# Z3 / TLA+ / Lean の役割分担

形式ツールが強くするのは**仕様の側** (一貫性・網羅性・空虚さ・規則との整合) で、実装の適合はテスト (ベクタとトレースの照合) で見る。この区別を崩さない。

| 層 | ツール | 対象 | 保証すること | 保証しないこと |
| --- | --- | --- | --- | --- |
| 状態なし | Z3 (`trs check`) | UC ごとの 入力→結果 の決定表 | 空虚な AC がない、未定義の入力がない (または OI として既知)、AC 間の矛盾がない、規則を満たす | AC が意図通りか |
| 状態あり | TLA+ / TLC (`trs tla`) | 画面遷移、リトライ、並行操作 | 規則 (不変条件) が全到達状態で成り立つ、各 AC の事後条件に到達できる | モデルが実装を正しく抽象化しているか |
| 計算の中核 | Lean 4 (任意) | 金額・期間・権限継承など無限領域の計算 | 規則が全入力で成り立つ (証明) | 実装がモデル通りか (差分テストで見る) |

## Z3

`trs check` が自動で行う。人も Claude も SMT を直接書かない。

- 決定表の変換は機械的 (LLM を通さない)。同じ構文木の Python 評価器と Z3 変換の一致を自己照合する (X001)。
- 未定義領域は部分割り当て (cube) に一般化し、1変数だけ違う cube はまとめて表示する。出力の式はそのまま OI の `region` に貼れる。
- 入力が列挙値でない (数値の範囲・文字列長) 振る舞いは、境界で区切った水準 (`0`, `1..上限`, `上限超`) に落として表す。区切りの妥当性は人が決める。

## TLA+

状態を持つ UC にだけ使う。全 PBI に書かない (コストに見合わない)。

### 所有の分担

| 部分 | 所有 | 理由 |
| --- | --- | --- |
| `TypeOK`、`Inv_*` (rules[].tla) | 人 | オラクル。AI が書くと、モデルに合わせて弱い不変条件を書き、通ってしまう |
| `Init`、アクション、`Next` | AI の下書き可 | 入力生成側。誤りは witness と人のレビューで検出する |
| `Witness_*` (acs[].tla_witness) | 人がレビュー | 「この状態に到達しない」という主張。TLC に破られることで到達可能性を示す |

### witness の考え方

不変条件の検査は「悪い状態に到達しない」しか示さない。モデルが何もしない (どこにも進まない) と、不変条件は全部空虚に通る。そこで AC ごとに「事後条件に到達しない」という主張を witness として置き、**TLC がそれを破ること**を要求する。破られなければ、その AC はどの実行でも満たされない (L030)。反例は最短の実行例なので、そのまま状態遷移テストのシナリオになる。

### 配線 (ファイルと trs.yaml)

1. `templates/Model.tla` と `templates/Model.cfg` を trs.yaml と同じディレクトリに `<名前>.tla` / `<名前>.cfg` としてコピーし、先頭の `---- MODULE Model ----` をファイル名に合わせて書き換える (SANY はモジュール名とファイル名の一致を要求する)
2. trs.yaml に `tla: {module: <名前>.tla, config: <名前>.cfg}` を書く (trs.yaml からの相対パス)。参照があるのにこの節が無いと S070、ファイルが無いと L001、非 ASCII の行があると L002
3. 規則は `rules[].tla` に不変条件名を、AC は `acs[].tla_witness` に witness 名を書く

.cfg に書くもの:

| 行 | 要否 |
| --- | --- |
| `SPECIFICATION Spec` | 必須。モジュール側の `Spec == Init /\ [][Next]_vars` を指す |
| `INVARIANT TypeOK` | 慣習。型の崩れを最初に捕まえる |
| `INVARIANT <rules[].tla の名前>` | 規則ごとに1行。モジュールに `名前 ==` の定義が無いと L010、.cfg に名前が無いと L011 |
| `INVARIANT <acs[].tla_witness の名前>` | **書かない。** witness は破られるための主張なので、本検査が落ちる (L020) |

`trs tla` は、まず .cfg のまま本検査を回し、次に witness ごとに「.cfg + `INVARIANT <witness>`」の一時 config で回して、反例を `generated/traces/<AC 完全 ID>.json` に落とす。一時 config はモジュールと同じディレクトリに作るので、そこは書き込み可能である必要がある。L011 は .cfg 内に名前があるかを見るだけなので、`INVARIANT` 行に置いたか (= TLC が実際に検査するか) は人が確かめる。

完成例: `tool/examples/PBI-123/Settings.tla` と `Settings.cfg` (trs.yaml の `rules[].tla: Inv_KeepDraftOnError` と `acs[].tla_witness: Witness_RetrySaved` に対応)。

### 書くときの落とし穴 (実際に踏んだもの)

- **SANY は ASCII しか受け付けない。** コメント内の日本語でも構文エラーになる。日本語は trs.yaml に書き、TLA+ には ASCII だけ書く (`trs tla` が L002 で事前に止める)。
- **コメント内に閉じ記号の2文字 (アスタリスク + 閉じ括弧) を書かない。** `(Inv_*)` のような表記でブロックコメントが閉じ、続きが構文エラーになる。
- **終端状態で止まると deadlock 扱いになる。** 終了状態に `UNCHANGED vars` の自己遷移を置くか、config に `CHECK_DEADLOCK FALSE` を書く。
- **状態爆発。** 定数は小さく (ユーザー2人、項目2件など)。抽象化の粒度はテスト可能性で決める。
- **活性 (いつか完了する) は公平性の仮定次第。** `WF` は「ずっと可能なら起きる」、`SF` は「何度も可能になるなら起きる」。リトライが失敗し続ける可能性を含むモデルで「いつか保存される」を言うには SF が要る。活性を規則にするときは、公平性の仮定自体を人がレビューする。

### スケール

TLC (明示状態) で足りなければ Apalache (記号的、内部で Z3) を検討する。どちらも TLA+ のまま使える。

## Lean 4 (任意)

列挙値の決定表なら Z3 で決着がつくので不要。使うのは次の場合だけ:

- 「どの金額でも端数処理後の合計が一致する」のような、有限個の値を試すだけでは示せない性質を保証したい
- その計算が事業上重大で、仕様の誤りのコストが高い

使い方:

1. 計算を Lean で参照モデルとして書く (実装言語では書かない)
2. 規則を定理として述べ、証明する (`theorem rule_R05 : ∀ x, ...`)。定理の文 (statement) は人が所有し、証明は AI が書いてよい。定理の文が意図通りかは Gap A なので、人がレビューする
3. 参照モデルを実行可能にし (`#eval` / コンパイル)、実装と同じ入力で突き合わせる差分テストを置く。入力は trs のベクタ + ランダム生成

証明されるのは参照モデルであって実装ではない。実装との関係は差分テストで見る。

## 検査結果の読み方

- `trs check` が通った → 仕様は内部的に一貫し、網羅し、規則を満たす。**意図通りかは別。**
- `trs tla` が通った → 規則は全到達状態で成り立ち、各 AC の事後条件に到達できる。**モデルが実装を正しく写しているかは別。**
- `trs trace` が通った → 全ベクタで実装の観測結果が仕様と一致した。**アダプタの観測が実装を見ているかは「壊して落ちるか」で確かめる。**
