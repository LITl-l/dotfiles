# 仕様 (trs.yaml) の作成を手伝う

Claude の役割は「人が振る舞いを決めるのを手伝う書記と、矛盾・抜けを指摘する検査役」。振る舞いを決める主体ではない。人が把握していない AC が trs.yaml に入った時点で、それは人が所有する仕様ではなくなる。

## ループ

```
資料を読む → 下書き → trs check → 指摘を人に質問として返す → 人が決める → 反映 → trs check …
```

Z3 の指摘 (特に Z020 未定義) は、**人への質問のリスト**として扱う。Claude が自分で埋めて消してはいけない。

## 手順

1. **一次資料を登録する。** 仕様書・デザイン・合意事項を `sources` に `SRC-n` として登録する。`rev` (版) が分からなければ人に聞く。
2. **因子と結果を洗い出す。** 「何が変わると振る舞いが変わるか」を因子に、「何を観測すれば正しいと言えるか」を結果にする。振る舞いを変えない値は因子にしない。資料で水準が確定していなければ `tentative` にして OI を起票する。
3. **UC と 3分類の枠を作る。** `scope` は最初すべて `未検討` にしておく (lint が止めるので、検討漏れが残らない)。
4. **AC を下書きする。** 正常 → 例外 → 準正常 の順に、資料から読み取れる振る舞いだけを書く。`pre` は資料の条件をそのまま式にし、`post` は結果の水準を選ぶ。`given/when/then` は人が読む文で書く。
5. **規則を書く。** 「常に〜」「決して〜」は AC ではなく `rules` に。状態を持たなければ `expr`、状態を持つなら `tla` (`formal.md`)。
6. **`trs check` を回す。** 出た指摘を次のように扱う:

| 指摘 | Claude がすること |
| --- | --- |
| Z020 未定義 | 「この入力のとき何が起きるべきか資料にありません」と、式 (そのまま region に使える) と具体例を添えて人に聞く。選択肢: AC を追加 / 起こりえないので前提にする / 未定として OI (region) にする |
| Z030 矛盾 | 2つの AC と反例を示し、どちらが正しいか、または資料の食い違いかを人に聞く |
| Z040 規則違反 | 規則と AC のどちらが誤りかを人に聞く。結果が未規定なら outcomes / post の追加を提案 |
| Z010 空虚 | 前提か pre の誤り。どちらの意図かを人に聞く |
| S050 未検討 | 「この UC の準正常は資料にありません。なしでよいですか、未定義として OI にしますか」と聞く |
| S031 根拠が実装 | 根拠を仕様書・デザインに差し替える。資料に無いなら未定義として OI |

7. **人のレビューを依頼する。** `trs gen` で `generated/TRS.md` を作り、AC を分類別に要約して「この内容で認識が合っているか」を確認してもらう。lint が通ったことは、構造が正しいことを示すだけで、意図通りであることは示さない。

## 根拠の規則

- 期待値の根拠は仕様書とデザイン (と記録された合意)。**実装ではない。**
- 実装を見てよいのは「その入力状態を作れるか (テスト可能か)」を確かめるときだけ。
- 資料に書かれていない振る舞いは未定義。推測やもっともらしい既定値で埋めない。

実装から期待値を作ると、テストは「コードがコード通りに動くこと」の確認になり、仕様と実装のズレは定義上ひとつも見つからない。AI はこれを自然に、しかももっともらしい文章でやってしまう。

## 人が決めること (Claude が決めないこと)

- 資料間の食い違いの採否
- 3分類の「なし」判断
- 未定義領域を AC にするか、前提にするか、OI にするか
- 水準の確定 (列挙の過不足、境界値)
- `coverage: all` にすべき AC (既定は pairwise)
- 不変条件 (TLA+ の Inv_ 定義と rules[].tla)

## Gherkin / BDD からの移行

| Gherkin | trs.yaml |
| --- | --- |
| `Scenario Outline` の `<変数>` と `Examples` の列 | `factors` (列名 = 因子、列に出る値 = 水準の候補) |
| `Given` | `given` (人が読む文) と `pre` (式) |
| `When` | `when` |
| `Then` | `then` (人が読む文) と `post` (結果の水準) |
| `Background` | 共通の `given`。**宣言済みの因子**について「その水準は起こりえない」と狭めているときだけ `assumptions` (`expr` は因子しか参照できない — S041。因子に無いことを言う Background のために因子を起こさない) |
| `Scenario` 1つ | AC 1つ。`Examples` の各行は AC でもベクタでもなく水準の実例。ベクタは水準の組合せから生成されるので、数値列を境界で水準に区切れば複数行が同じ水準に落ちて 1 ベクタになる (3000円 と 50000円 が同じ帯なら 1 本。`formal.md` の Z3 節) |

落とし穴:

- `Then` の文に期待値が埋まっている (「エラーが表示される」) → `outcomes` の水準にして `post` に書く。`then` の文だけでは検査されない
- `Examples` の列がすべて因子とは限らない。振る舞いを変えない値 (氏名、ID) は因子にしない。逆に列に出た値は実例であって水準の全体ではないので、資料で列挙が確定しなければ `tentative` + OI
- Scenario が無い領域は「振る舞いが無い」ではない。移行後に Z020 が出たら、元の feature に無いという理由で埋めず、OI (`region`) にして人に聞く

## よくある失敗

- 1つの AC に複数の結果を詰める → post が増えたら分割を検討する
- 「起こりえない」と「決まっていない」の混同 → 決まっていないなら OI
- 因子の増やしすぎ → 入力空間が上限 (20万) を超えたら UC を分割する。振る舞いを変えない値は因子にしない
- OI を解決後に消す → `resolved` と `resolution` を残す。半年後に「なぜこの仕様か」を辿るため
- `then` にだけ書いて `post` にない期待 → 検査されない。必要なら outcomes に加える
