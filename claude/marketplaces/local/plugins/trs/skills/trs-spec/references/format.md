## 1. 全体像と意味論

各 UC は「入力 (因子の組) → 結果」の**部分関数**を定義する。形としては、因子を条件・結果を動作とする**決定表** (decision table) で、各 AC がその1列 (入力空間の1領域とそこでの結果) に当たる。

- `inputs` の因子の直積が UC の入力空間
- `assumptions` は起こりえない入力を除外する (例: 閲覧者には削除ボタンが表示されない)
- 各 AC は `pre` (入力空間の部分領域) と `post` (その領域で観測される結果) の組
- Z3 で次を検査する:
  - **空虚さ**: `pre` を満たす入力が前提の下で存在するか
  - **網羅性**: どの AC にも当たらない入力が残っていないか (残りは「未定義」)
  - **一意性**: 重なる AC の結果が食い違わないか
  - **規則**: 全 AC が `rules[].expr` を満たすか

入力の扱いは3種類に分かれ、混同しないことが運用上もっとも重要:

| 種類 | 書く場所 | 意味 | 検査上の扱い |
| --- | --- | --- | --- |
| 規定済み | `acs[].pre` | 振る舞いが決まっている | ベクタ生成対象 |
| 起こりえない | `assumptions` | 入力として発生しない (根拠必須) | 検査・生成の対象外 |
| 未定義 (既知) | `open_issues[].region` | 決まっていないことを認識済み | Z021 (情報)。AC がこの領域を規定するとエラー |
| 未定義 (未知) | どこにもない | 誰も気づいていない | **Z020 エラー** |

「起こりえない」に逃がすのは、本当に起こりえないと資料で言えるときだけ。決まっていないだけなら OI にする。

状態を持つ振る舞い (画面遷移、リトライ、並行操作) は TLA+ で書き、`rules[].tla` (不変条件) と `acs[].tla_witness` (到達可能性) で trs.yaml と結ぶ (`formal.md`)。

## 2. 各セクション

| キー | 必須 | 内容 |
| --- | --- | --- |
| `schema` | ✓ | `trs/v2` |
| `id`, `title` | ✓ | PBI ID とタイトル |
| `sources` | ✓ | `{id: SRC-n, kind, ref, rev}`。kind は 仕様書/デザイン/合意/規格/議事録。**実装は不可**。rev は必須 |
| `factors` | ✓ | `{id, label, levels, status: fixed/tentative, basis}` |
| `outcomes` | ✓ | `{id, label, levels}`。観測できる結果の列挙 |
| `assumptions` | | `{id: A-n, text, expr, basis, use_cases?}`。因子のみの式 |
| `rules` | | `{id: R-n, ears, text, basis}` + `expr` (状態なし) か `tla` (状態あり) のどちらか一方 |
| `stories` | | `{id: US-n, as_a, i_want, so_that}` |
| `use_cases` | ✓ | `{id: UC-n, story, title, inputs, scope, acs}` |
| `use_cases[].scope` | ✓ | `{正常, 準正常, 例外}` に あり/なし/未検討。未検討はエラー |
| `use_cases[].acs` | ✓ | `{id, title, given?, when?, then?, pre, post, coverage?, tla_witness?, basis}` |
| `tla` | | `{module, config}` (trs.yaml からの相対パス) |
| `open_issues` | ✓ | `{id: OI-n, text, status, affects?, region?, use_case (region があれば必須。実在する UC-n を指すこと), link?, resolution?}` |

### 根拠 (`basis`)

`basis` は 因子 (`factors`)・前提 (`assumptions`)・規則 (`rules`)・AC (`use_cases[].acs`) の4か所にあり、すべて同じ検査を受ける。

- `SRC-n` か `OI-n` をひとつ以上含むこと (S032)。参照先が実在すること (S033)
- **`OI-n` を根拠にできるのは `status: resolved` のときだけ。** open な OI を根拠にすると S034 (エラー)。決まっていないものは根拠ではなく、`affects` / `region` でブロックや未定義として扱う
- コードパスを指す書き方はエラー (S030 は `sources[].ref`、S031 は `basis`)

### 規則の EARS 分類

`rules[].ears` は規則の型。文の形が決まるので、「〜を考慮すること」のような検査できない書き方を避けられる。

| 値 | 文の形 | 選ぶとき |
| --- | --- | --- |
| `ubiquitous` | システムは常に〜しなければならない | 前件なしで常に成り立つ |
| `event` | `<トリガ>` のとき、システムは〜しなければならない | 単発の事象が引き金 |
| `state` | `<状態>` である間、システムは〜しなければならない | ある状態が続く間だけ成り立つ |
| `unwanted` | `<望まない条件>` の場合、システムは〜しなければならない | 失敗・エラー・不正入力への応答 |
| `optional` | `<機能>` が有効な場合、システムは〜しなければならない | 構成・契約で有無が変わる機能 |
| `complex` | 上記の組み合わせ | 前件が複数の型にまたがる |

EARS の前件 (トリガ・状態・条件) は `expr` では `=>` の左辺になる。`ubiquitous` でも対象の入力を絞るなら `=>` を使う (例: R-01)。左辺が決して成り立たないと Z043。`expr` と `tla` のどちらを書くかは分類では決まらない。後件が1つの UC の 入力→結果 の行で言えるなら `expr`、遷移や順序をまたぐなら `tla`。

### 規則が当たる UC と、`post` で固定していない結果

- 規則が適用される UC は `expr` に出てくる**因子**で決まる。その因子が UC の `inputs` にそろっていればその UC に適用される
- **因子をまったく参照しない規則 (結果だけの式) は、全 UC に適用される。** そろえるべき因子が空なので常に「そろっている」と判定される。この型の規則は Z042 (どの UC にも適用されない) にもならない
- 検査は AC ごとに 「前提 ∧ `pre` ∧ `post` ∧ ¬規則」 が充足可能かを見る。**`post` で固定していない結果は Z3 から見て自由変数**なので、規則が触れる結果を `post` に書いていない AC は Z040 になる (メッセージに「この AC は結果 [...] を規定していません」が付く)
- よって「税込欄には常に税込額を表示する」のような全 UC に当たる規則をひとつ足すと、無関係に見える AC まで その結果を `post` に書く必要が出る。対象を絞りたいなら、上記のとおり `=>` の左辺に因子の条件を置く

### 振る舞いの3分類

事後条件 (UC のゴール) を達成できたかで決める。

| 分類 | 説明 | 事後条件 |
| --- | --- | --- |
| 正常 | まっすぐ成功する | 達成 |
| 準正常 | ハンドリング済みのエラーが起きるが、再操作などで完了できる | 達成 |
| 例外 | UC が中断し、完了できない | 不達 |

### given / when / then と pre / post の関係

- `given` `when` `then` は人が読む説明文。`<factor_id>` で因子を参照してよい
- `pre` `post` は機械が検査する形式的な定義
- 両者の一致は機械では保証できない (Gap A)。レビューで人が確認する。`then` に書いたが `post` で表現していない期待 (例: トースト表示) は検査されないので、検査したいなら `outcomes` に加える

### `region` の書き方 — 絞りすぎない

Z3 は未定義領域を**一般化した cube** (= 任意の水準でよい因子を落とした部分割り当て) として出す。OI の `region` がその cube を**丸ごと含む**ときだけ Z021 (既知) に変わり、含まなければ Z020 (エラー) のまま残る。「正確に」書こうとして因子を足すほど cube を覆えなくなり、何にも当たらないまま Z020 が消えない。

書く前に判断する基準:

- `region` は Z020 の cube を**含む**こと。かつ 同じ UC のどの AC の `pre` とも**交わらない**こと (交わると Z060)。この2つの間が書ける範囲
- 迷ったら Z020 のメッセージの式をそのまま貼る。あれが cube そのもの
- 複数の OI で分担しても覆えない。cube はどれか**1つ**の OI の `region` に収まっている必要がある
- 判定に使われるのは `status: open` かつ その UC を `use_case` に指す OI だけ。OI を `resolved` にすると その領域は再び Z020 になる。resolve する前に AC で埋める

### ブロック

次の AC はブロック中とし、ベクタを生成しない。実装エージェントも着手しない。

- open な OI の `affects` に AC の完全 ID がある
- UC の `inputs` にある因子が open な OI の `affects` にある、または `tentative`

## 3. 条件式の言語

CEL のサブセットに含意 `=>` を足したもの。

```
role == "管理者"            role != "閲覧者"
role in ["管理者", "編集者"]
A && B      A || B      !A      ( ... )      A => B      true      false
```

- 左辺は因子・結果の id (ASCII のみ。4 を見よ)、右辺は文字列リテラル (日本語可)
- `pre` と `assumptions` は UC の入力因子のみ、`rules[].expr` は因子と結果を使える
- `=>` は右結合、優先順位は `!` > `&&` > `||` > `=>`

検査器は同じ構文木から Python の評価器と Z3 の式を作り、有限領域で両者の一致を照合する (X001)。

## 4. ID の規則

- **因子 (`factors[].id`) と結果 (`outcomes[].id`) の id は ASCII のみ**: `^[A-Za-z_][A-Za-z0-9_]*$` (先頭は英字か `_`、以降は英数字か `_`)。日本語を書く場所は `label` と `levels` で、式では右辺の文字列リテラルに出る。破ると S000
- AC の完全 ID: `US-01_UC-01_AC-基本正常-001` (`<story>_<uc>_<ac.id>`)
- AC の id: `AC-<フロー><分類>-<3桁>`。フロー = 基本/代替/例外、分類 = 正常/準正常/例外
- ベクタ ID: `<AC 完全 ID>#<入力の sha256 先頭8桁>`。水準の並び順を変えても同じ入力なら同じ ID
- **ID は付け直さない。** 廃止した AC の番号は再利用しない (過去のテスト結果・議論との対応が壊れる)

## 5. 生成物 (`<spec dir>/generated/`)

| ファイル | 生成 | 内容 |
| --- | --- | --- |
| `TRS.md` | `trs gen` | 人がレビューする Markdown ビュー |
| `vectors.json` | `trs gen` | テストベクタ (`format: trs-vectors/v1`, `spec_sha256`, `vectors[]`, `blocked[]`, `stats[]`) |
| `traces/<AC>.json` | `trs tla` | witness の反例トレース (状態遷移テストの入力) |

`TRS.md` と `vectors.json` はコミットし、CI で `trs gen --check` により trs.yaml との一致を検査する。`spec_sha256` は YAML の書式に依存しない内容ハッシュ。

### 組み合わせの生成 (`coverage`)

AC ごとに、UC の入力因子の直積から 前提 と `pre` を満たす組み合わせを列挙し (= その AC の**領域**)、その中からベクタを選ぶ。

- 既定は `pairwise`。2因子の水準の組をすべて1回は含む行集合を、決定的な貪欲法 (未網羅の組を最も多く埋める行から採る) で選ぶ。同点は水準の記載順で先勝ち
- `coverage: all` は領域を全件出す。入力が1因子の UC は既定でも全件
- 候補は領域の中だけなので、前提や `pre` で起こりえない組は最初から要求されない
- 削減の度合いは `vectors.json` の `stats[]` で見る (`region` = 領域の件数、`vectors` = 生成した件数)
- 直積は前提で絞る**前**に数える。上限 20万 を超えると生成が止まる (G001)。UC を分割する

`all` にする基準: 結果が3因子以上の同時の組み合わせで決まる (pairwise が保証するのは2因子まで)、または領域が小さく全件でも安い。どの AC を `all` にするかは人が決める。

## 6. 検査コード一覧

E = エラー、W = 警告 (`--strict` で失敗)、I = 情報。

| コード | 内容 |
| --- | --- |
| S000 | スキーマ違反 |
| S010 | 式の構文エラー |
| S020 / S021 | id の重複 / 因子と結果の id 衝突 |
| S030 | `sources[].ref` が実装 (コードパス) を指している |
| S031 | `basis` の文が実装 (コードパス) を指している |
| S032 | `basis` に `SRC-n` / `OI-n` がひとつも含まれない |
| S033 | `basis` が参照する `SRC-n` が `sources` に、`OI-n` が `open_issues` にない |
| S034 | `basis` が参照する `OI-n` が未解決 (`status: open`) |
| S040–S048 | 参照: ストーリー・入力 / 式の変数 / 水準 / post / then なし (W) / 前提の UC / OI の affects / OI の resolution / region の use_case |
| S050–S052 | 3分類の枠: 未検討 / あり なのに AC なし / なし なのに AC あり |
| S060 / S061 | 未使用の因子 (W) / tentative なのに open な OI がない (W) |
| S070 | tla 参照があるのに `tla` 設定がない |
| Z010 | 空虚な AC (前提の下で pre を満たす入力がない) |
| Z020 | 未定義の入力領域 (メッセージの式はそのまま `region` に貼れる) |
| Z021 | 既知の未定義 (OI の region 内) |
| Z030 / Z031 | 重なる AC の結果が食い違う / 重なるが結果は同じ (W) |
| Z040 | 規則違反 (反例つき。AC が規則の結果を規定していない場合はその旨を表示) |
| Z042 / Z043 | どの UC にも適用されない規則 (W) / 前件が成り立たない空虚な規則 (W) |
| Z050 | 前提により起こりえない水準 (W) |
| Z060 | open な OI の region を AC が規定している |
| X001 | 評価器と Z3 変換の食い違い (検査器のバグ) |
| I000 | 要約: AC 本数 (正常 / 準正常 / 例外の内訳)、ブロック中の本数、open な OI 件数。`trs check` が必ず出す (I) |
| I001 | 式・参照のエラー (S010 / S040–S043) があるため Z3 の意味検査を省略した。Z0xx が出ないのはこれが理由 (I) |
| I090 | その AC はブロック中 (理由つき)。ベクタを生成しない。ブロック中の AC を報告するときの機械可読の根拠 (I) |
| G000 / G001 / G010 | 検査エラーのため生成せず / 入力空間が上限超過 / 生成物の乖離 |
| L000–L031 | TLA+: TLC なし / ファイルなし / 非 ASCII / 定義・config に名前なし / 本検査失敗 / witness が破られない (到達不能) / 想定外 |
| T000–T011 | 照合: vectors.json なし / 未実行 / 失敗 / skip / 未知の ID / テストが古い仕様 / ベクタが古い |
